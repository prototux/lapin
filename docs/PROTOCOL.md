# Device protocol

Every client talks to the server over one WebSocket: the ReSpeaker satellites,
the browser "Talk" page, and the phone and desktop apps.

    ws://<server>:<gateway_port>/v1/device      (default port 8765, `server.gateway_port`)

- **Text frames** are JSON objects. Each one has a `"type"`.
- **Binary frames** are audio. The first byte says which direction:
  - `0x01` + PCM: microphone audio, device → server. Always 16 kHz, mono, signed 16-bit little-endian. Send 20–40 ms per frame (640–1280 bytes after the header byte).
  - `0x02` + u32 little-endian stream id + PCM: audio for playback, server → device. The format is the one announced by `stream_open`.

The server does speech detection and end-of-turn detection itself. A device only
starts a turn and streams the microphone until the server says `eot`; it doesn't
need its own voice detection.

## 1. Connecting and pairing

The first message must be `hello`:

```json
{"type": "hello", "protocol": 1,
 "device_id": "phone-3f9a1c2e", "token": "<random secret, generated once and stored>",
 "kind": "phone", "name": "Pixel d'Alice", "room": "", "owner": "alice",
 "version": "1.0.0",
 "capabilities": {"audio_in": {"rate": 16000, "channels": 1, "format": "s16le"},
                  "audio_out": {"rates": [24000, 48000], "channels": [1, 2], "format": "s16le"},
                  "confirm_ui": true, "display": true},
 "tools": [ ... see section 5 ... ]}
```

**Fields:**

- **`kind`:**
  - `satellite` (ReSpeaker), `phone`, `tv`, `desktop`.
  - `browser` is reserved for the admin UI's Talk page.
  - Music for "everywhere" and room announcements only go to `satellite` devices. A personal device only gets audio for its own turns.
- **`device_id` and `token`:** generated by the device on first start and kept forever. Use a UUID and 32 random bytes in base64url. A new id stays waiting until it's approved on the admin UI's Devices page (or approved automatically if `server.auto_approve` is set). While waiting, the server sends `{"type": "pending", "message": ...}` and keeps the socket open.
- **`owner`:** the household user this device belongs to (lower case, as on the People page). On the first pairing, if that user exists, the device is bound to them permanently. Requests from it then use that person's memory, accounts (Jellyfin, Navidrome) and language. The admin can change it on the Devices page.
- **`capabilities.confirm_ui`:** the device can show Yes/No buttons for confirmations (section 6).
- **`tools`:** actions the device runs itself (section 5).

**Replies from the server:**

- `{"type": "welcome", "server": "...", "version": "...", "server_time_ns": 123, "config": {"name": ..., "room": ...}}` once accepted.
- `{"type": "error", "message": "..."}`, followed by the server closing the socket. Possible reasons: wrong token, blocked device, rejected device.

**Reconnecting:** reconnect with a backoff of 1, 2, 5, then 10 s (capped). The server pings every 20 s at the WebSocket level.

**Optional:** `{"type": "ping", "t0": <ns>}` is answered with `{"type": "pong", "t0": ..., "t1": <server ns>}`.

## 2. A voice turn

```
device                                   server
  | wake {wake_id:1, source:"button"} -->  |
  | 0x01 PCM ... (stream continuously) -->  |   speech detection + end of turn
  |                       <-- wake_ack      |
  |                       <-- transcript    |   (partial, final:false; then final)
  |                       <-- eot           |   stop sending the microphone
  |                       <-- transcript    |   final:true
  |                       <-- stream_open   |   {id:7, kind:"tts", rate:24000, channels:1}
  |                       <-- 0x02 PCM ...  |
  |                       <-- reply         |   {text:"..."} the full answer text
  |                       <-- stream_close  |   {id:7, drain:true}
  |                       <-- session_end   |   {follow_up:true, follow_up_ms:6000}
```

**What the device sends:**

- **`wake`:**
  ```json
  {"type": "wake", "wake_id": 1, "source": "button", "score": 1, "preroll_ms": 0}
  ```
  - `wake_id` goes up by one with each turn.
  - `source` is one of:
    - `button`: assistant key, tap, hotkey. No wake-word check.
    - `followup`: the device reopened the microphone because `session_end.follow_up` was true.
    - `kws`: on-device wake word (satellites only; the server then checks the keyword).
  - Start streaming the `0x01` audio immediately after `wake`.
- **`audio_end`:** `{"type": "audio_end", "wake_id": 1}` when the user ends the turn by hand (tapping the mic again, releasing push-to-talk). The server then transcribes what it got. Stop streaming afterwards.
- **`button`:** `{"type": "button", "action": "cancel"}` aborts the current turn. `{"type": "button", "action": "stop"}` stops this device's music or alarm.

**What the server sends during a turn:**

- **`wake_ack`:** `{"wake_id": 1}`. The turn was accepted. Nothing to do.
- **`eot`:** `{"wake_id": 1}`. End of turn: stop sending the microphone and show "thinking".
- **`cancel`:** `{"wake_id": 1, "reason": "no_speech" | "empty" | "rejected" | "barge_in" | "button" | ...}`. The turn is over without an answer. Stop the microphone and go idle. `no_speech` / `empty` mean nothing was understood ("I didn't hear anything").
- **`transcript`:** `{"text": "...", "final": bool}`. What was heard, for display.
- **`reply`:** `{"text": "...", "ack": ""}`. The answer as text, for display. It arrives once the answer is complete. `ack` is set (for example `"done"`) when the action needed no sentence: show a check mark.
- **`session_end`:** `{"follow_up": bool, "follow_up_ms": 6000}`. The turn is finished.
  1. Let the playback buffer drain first.
  2. If `follow_up` is true, the answer was a question: reopen the microphone with a new `wake` whose `source` is `followup`.
  3. If nobody speaks, the server ends that turn with `cancel` (`no_speech`).
- **`earcon`:** `{"name": "done" | "error" | "notify" | "wake" | ..., "loop": false}`. Play a short system sound. `done` is the "OK" chime for actions with no spoken answer.
- **`stop`:** `{"media": true}`. Stop all playback now (the user said "stop").
- **`listen`:** `{"timeout_ms": 6000, "earcon": false}`. The server asks the device to open the microphone, for example after a question it announced. Answer with a `wake` whose `source` is `followup`.
- **`set`:** `{"volume": 0-100, "mic_muted": bool}`. Apply if supported.
- **`led`:** `{"pattern": "success" | ...}`. Satellite LED ring hints. Other devices can ignore it or map it to their UI.

**Barge-in:** a new `wake` during an answer interrupts it. The server aborts the old turn, so the device should also stop its playback immediately.

## 3. Playback streams

- **`stream_open`:**
  ```json
  {"type": "stream_open", "id": 7, "kind": "tts" | "media" | "alarm" | "chime",
   "rate": 24000, "channels": 1, "gain_db": 0, "start_at_ns": 0, "prebuffer_ms": 300}
  ```
  - Speech (`tts`) is 24 kHz mono.
  - `media` (radio, music) is usually 48 kHz stereo.
  - `start_at_ns` (server clock) is for synchronized multi-room playback. Personal devices can ignore it and play as soon as about 150 ms is buffered.
- **Audio:** binary `0x02` frames carrying the stream id.
- **`stream_close`:** `{"id": 7, "drain": true}`. With `drain` true, play what's buffered and then release. With `drain` false, drop it now.
- **`stream_pause`:** `{"id": 7, "paused": bool}`.

Several streams can be open at once (speech over music). While speech plays, lower music by about 18 dB, and by 40 dB while the microphone is open.

Optional: report `{"type": "playback", "id": 7, "event": "started" | "finished"}`.

## 4. Typed requests

- **Device → server:** `{"type": "text", "text": "Mets du Daft Punk", "speak": true}`.
  - The answer comes back as `reply`, followed by `session_end`, exactly like a voice turn.
  - With `speak` true, the answer is also spoken through a `tts` stream.
  - A device's typed turns run one at a time.

## 5. Device tools (phone and computer actions)

A device can offer actions that the assistant's language model may call, the way
an LLM uses tools. They're declared in `hello.tools`, or replaced at any time with
`{"type": "tools", "tools": [...]}`:

```json
{"name": "send_message",
 "description": "Send a text message to a contact by SMS or Signal.",
 "parameters": {"type": "object",
                "properties": {"contact": {"type": "string", "description": "contact name or number"},
                               "message": {"type": "string"},
                               "app": {"type": "string", "enum": ["sms", "signal"]}},
                "required": ["contact", "message"]},
 "confirm": true,
 "summary": "send “{message}” to {contact} ({app})",
 "silent": false}
```

**Fields:**

- **`name`:** `[a-z][a-z0-9_]{1,40}`. Server tools with the same name win, so avoid generic names that the server already uses (`set_volume`, `set_timer`, `play_radio`...).
- **`description` and `parameters`:** JSON Schema, as for OpenAI function calling.
- **`confirm`:** the action needs an explicit "yes" before it runs (messages, calls, anything irreversible).
- **`summary`:** template for the confirmation question, filled with the arguments.
- **`silent`:** the action speaks for itself (opening an app, the flashlight). The server answers with the "done" chime instead of a sentence.
- **`replaces`:** names of server tools this device does better itself, e.g. `["subsonic_play", "jellyfin_play_music"]` for a phone that plays music in its own Subsonic app. Those server tools are hidden for this device's requests, and the "mets du …" fast path calls this tool with `{"query", "kind"}` instead.

Two tool names have a special role in the fast paths:

- **`phone_media`** (`action`: play | pause | next | previous): used for "suivante", "pause"... when the server isn't playing anything on this device.
- **`phone_now_playing`** (no arguments): used for "c'est quoi cette musique ?". Return `{"title", "artist", "album", "app", "playing"}`.

These tools are offered only for requests made on that device. A phone's tools are
never used for a request made on a satellite or in a chat.

**Calling a tool:**

- **Server → device:** `{"type": "tool_call", "call_id": "c12", "name": "start_navigation", "args": {"destination": "Gare de Lyon"}}`.
- **Device → server, within 20 s:** `{"type": "tool_result", "call_id": "c12", "result": {...}}`.
  - Keep the result short, factual and in English: `{"ok": true}`, `{"ok": true, "battery": 54, "charging": false}`, or `{"error": "no contact named Marie", "candidates": ["Marie Dupont", "Marie Leroy"]}`.
  - The model reads it to word its answer.
  - Use `error` for failures and missing permissions, for example `"error": "permission to send SMS not granted; ask the user to open the app"`.

## 6. Confirmations

When the model calls a tool with `confirm: true`:

1. The tool doesn't run yet. The server keeps it as the pending action.
2. The assistant asks: "Tu veux que j'envoie « J'arrive » à Marie par SMS ?".
3. A spoken "oui" / "yes" runs it, and "non" / "no" cancels it. The question ends with a follow-up, so the microphone reopens by itself.
4. A device with `capabilities.confirm_ui` also receives `{"type": "confirm", "summary": "...", "tool": "send_sms"}`. Show Yes/No buttons until `session_end` of the next turn, or until another turn starts.
5. A tap sends `{"type": "confirm_reply", "yes": true}`. That's the same as saying yes; the action then comes back as a `tool_call`.

The device itself must not ask for confirmation again before running a confirmed
`tool_call`. The server already did.

## 7. Other messages

- **Device → server:**
  - `{"type": "state", "state": "idle" | "listening" | "thinking" | "speaking", "muted": false}`: for the admin UI.
  - `{"type": "settings", "volume": 70, "mic_muted": false}`: when changed on the device.
  - `{"type": "telemetry", "system": {...}}`: optional.
- **Satellites only (wake words):**
  - `{"type": "wake_words", "wake_words": ["dis_lapin"]}`: the keywords this device listens for (the server verifies wakes against them).
  - `{"type": "wake_sample", "keyword": "dis_lapin", "wav_b64": "...", "sync": false}`: an enrollment recording (16 kHz mono 16-bit WAV). The server keeps one copy of each; `sync: true` = an existing one re-sent at connection.
  - `{"type": "wake_templates_get", "keyword": "dis_lapin"?}`: a device without its own enrollment (ESP32 satellite) asks for the recordings. The server answers with one `{"type": "wake_template", "keyword", "name", "wav_b64", "index", "count"}` per recording (about 85 KB each), then `{"type": "wake_templates_done", "count": n}`.

## 8. Embedded satellites: remote log and firmware updates

For boards without a convenient serial port (ESP32):

- **Log:** `{"type": "log", "reset_reason": "poweron" | "panic" | "brownout" | "task_wdt" | "int_wdt" | "sw" | ..., "boot_count": 12, "lines": ["I (5436) main: ...", ...]}`. Sent at every connection (including the lines from before a crash, kept in RTC memory) and when new errors appear; at most 200 lines / 16 KB per message. The server keeps the last 600 lines per device (Devices page → Device log) and logs crashes and error lines.
- **Firmware update (OTA), through this WebSocket:**
  1. Server → device: `{"type": "ota_begin", "size": N, "sha256": "<hex>", "version": "1.1.0"}`.
  2. Device → server: `{"type": "ota_status", "state": "ready"}`.
  3. Server → device: binary frames `0x03` + u32 LE offset + data (16 KB). The server stays at most 64 KB ahead of the last acknowledged offset.
  4. Device → server, after every 64 KB written: `{"type": "ota_status", "state": "receiving", "offset": N}`.
  5. Server → device: `{"type": "ota_end"}`. Device → server: `verifying`, then `done` (it restarts into the new image), or `{"state": "error", "error": "..."}` at any point.
  6. The new image marks itself valid only after it reaches the server and gets `welcome`; otherwise the bootloader goes back to the previous one.
